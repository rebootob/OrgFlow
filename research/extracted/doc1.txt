Professional Organization Charts in Kintone for OrgFlow

Executive summary

For OrgFlow’s current state—57 canonical organization nodes, 275 employees, stable 3.8.4F geometry, and a strict zero-write requirement for Apps 53/791/792/793—the best next step is not to replace the chart renderer. The lowest-risk architecture is to preserve the existing HTML card geometry and add a native SVG connector layer, optionally using only small D3 modules such as d3-zoom for viewport interaction. D3 is deliberately low-level, supports SVG/HTML/Canvas interaction, provides zoom/pan behavior, and includes hierarchy/tree algorithms, but it does not force OrgFlow into a new visual model. [1]

My preferred stack for OrgFlow is therefore:

Kintone Custom View + existing OrgFlow DOM + native SVG connector overlay + small D3 modules where useful.

For Phase 3.8.5, D3's tree layout should not replace the accepted layout. Use the current DOM as the geometry authority, obtain actual card coordinates with getBoundingClientRect(), convert them into canvas-local coordinates, and render canonical parent-child edges as orthogonal SVG paths behind the cards. getBoundingClientRect() is specifically standardized to return an element's bounding rectangle, while Resize Observer is standardized for responding to element-size changes; those two browser primitives match the geometry requirements that emerged from phases 3.8.4C–F. [2]

For a future full renderer replacement, my open-source fallback is Cytoscape.js + ELK. Cytoscape.js has first-class panning, zooming, fit/center APIs, graph models and a broad layout-extension ecosystem including ELK. It is a substantially larger migration because it would assume ownership of node positioning rather than preserving the HTML geometry you have already validated. [3]

If commercial licensing is acceptable and OrgFlow later prioritizes a turnkey diagramming engine over preserving its Kintone DOM, GoJS is technically very strong: it has an official organization-chart implementation, TreeLayout, Overview navigation, Canvas and SVG renderers, built-in zoom/scrolling, links/routing, exports, and read-only diagram mode. It is, however, commercially licensed rather than open source. [4]

For Kintone integration, OrgFlow should run as a direct JavaScript customization on a Custom View, initialized from app.record.index.show. That event fires after a record-list/custom-view display and supports asynchronous handlers through Promises. Read canonical data through kintone.api() using only GET operations; the Get Records endpoint returns up to 500 records per request, so the present 57-node/275-employee datasets fit comfortably within one request per current app if their records are separated as described. Kintone currently documents a domain concurrency limit of 100 API requests and a default daily limit of 10,000 requests per app, so four parallel read operations are well below the concurrency ceiling. [5]

Why D3/native SVG wins for the current OrgFlow phase

The crucial distinction is that Phase 3.8.5 is not a layout project anymore. Phases 3.8.4C–F already established and stabilized natural sizing, true scale, collision-free sibling placement and top-level branch visibility. Any library that automatically recalculates node positions now introduces unnecessary regression risk.

D3 fits differently from GoJS, OrgChart JS or Cytoscape: it can be used as a collection of primitives rather than a complete diagram owner. d3-zoom supports panning and zooming independently of whether the visible content is HTML, SVG or Canvas; d3-hierarchy is available later if OrgFlow ever chooses to replace the current layout. [14]

That permits this division of responsibility:

Canonical OrgFlow model        │        ├── Existing OrgFlow HTML renderer   ← DO NOT RE-LAYOUT IN 3.8.5        │        └── Connector adapter                 │                 └── SVG paths derived from real DOM anchors

The full-renderer fallback should be Cytoscape.js + ELK rather than immediately moving to another bespoke layout implementation. Cytoscape exposes explicit viewport zoom, pan, center and fit operations and supports external hierarchical layout adapters such as ELK. [3]

The commercial full-renderer alternative is GoJS. GoJS's Diagram owns its hosting DIV, draws to Canvas by default or can use an SVG renderer, manages zoom/scrolling/document bounds, provides layouts and routing, can produce SVG/image snapshots, and can operate in read-only mode. Its official organization-chart sample already demonstrates TreeLayout, navigation overview and search. [15]

BALKAN OrgChart JS is the easiest purpose-built option to evaluate if the company wants an org chart product rather than a visualization toolkit. Its official documentation includes org-specific relationships, exports and navigation, but its Community and Commercial licensing model must be factored into an internal Kintone deployment. [16]

Where Mermaid belongs

Mermaid is valuable in OrgFlow documentation, not as the interactive 275-person application renderer. Its core model is text-defined diagrams; flowcharts consist of nodes and edges, and diagrams can be produced from the JavaScript API or through the CLI. That is ideal for architecture diagrams, canonical-tree diagnostics, design documents and possibly deterministic documentation exports. [17]

Kintone integration architectures

Kintone's JavaScript customization API is well suited to a direct-in-app implementation. app.record.index.show is fired after the list/custom-view page is rendered and can return a Promise; the JavaScript API exposes kintone.api() for REST calls and record-list/header DOM integration methods. Kintone also supports Custom Views plus JavaScript/CSS customization, making the view itself a sensible host for OrgFlow. [18]

Lightweight DOM plus SVG overlay — recommended

This architecture keeps Phase 3.8.4F exactly where it is.

getBoundingClientRect() gives the rendered element rectangle; Resize Observer exists specifically to observe changes in element dimensions. SVG is a vector-graphics standard, making it suitable for scale-independent connector paths. [19]

The DOM structure should look approximately like:

<div class="orgflow-canvas">  <div class="orgflow-world">    <svg      class="orgflow-connectors"      aria-hidden="true"      focusable="false">    </svg>    <div class="orgflow-nodes">      <!-- Existing Phase 3.8.4F cards remain here -->    </div>  </div></div>

.orgflow-canvas {  position: relative;  overflow: auto;}.orgflow-world {  position: relative;  transform-origin: 0 0;}.orgflow-connectors {  position: absolute;  inset: 0;  overflow: visible;  pointer-events: none;  z-index: 0;}.orgflow-nodes {  position: relative;  z-index: 1;}

The decisive rule is:

.orgflow-world is the only zoom/pan transform authority.

Neither individual branches nor the SVG layer should receive separate scale factors.

This directly prevents the double-scaling problem that OrgFlow encountered in 3.8.4C.

Full renderer architecture — fallback

If OrgFlow later decides that maintaining a bespoke intrinsic-layout engine is too expensive, switch behind a feature flag to Cytoscape.js + ELK, or to GoJS if commercial licensing is approved.

Cytoscape's API exposes zoom bounds, user zoom/pan controls, fit/center operations and layout creation; ELK is available as a Cytoscape layout adapter. [3]

GoJS goes further toward a complete diagram application: its Diagram controls its Canvas/SVG representation, model, links, layouts, viewport, scrolling and scale. This convenience is also why adopting it would be a renderer migration, not a connector patch. [20]

Direct DOM versus iframe embedding

For OrgFlow today, use direct DOM integration. It allows kintone.api() to operate inside the user's current Kintone session and lets the connector layer measure the exact card elements already rendered by the application. Kintone documents kintone.api() as its JavaScript REST-request API, and Get Records accepts session authentication as well as other authentication methods. [21]

An iframe is more appropriate only if a future renderer becomes a separately deployed application. Its benefit is CSS/runtime isolation; its cost is a separate lifecycle, cross-window focus and sizing, and a data bridge. In that design I would not place Kintone API tokens into browser iframe code. Have the Kintone parent retrieve permitted data and send an immutable view model through postMessage, or use a controlled server-side authentication path.

Kintone also exposes kintone.proxy() when a customization must call an external API and needs to avoid browser CORS restrictions. [22]

For the current project:

Direct DOM wins decisively.

Geometry, connectors, and ES6 reference implementation

Read-only Kintone data access

The Get Records API is a GET endpoint and retrieves at most 500 records per request. For OrgFlow's current 57 canonical nodes and 275 employees, that ceiling is not a problem for a single app dataset of those sizes. Kintone's app.record.index.show handler can return a Promise, so initialization can await the complete read pipeline before rendering connectors. [23]

A production-safe wrapper should make methods other than GET impossible in the OrgFlow visualization module:

Kintone currently permits up to 100 concurrent API requests per domain; the four GETs above are therefore nowhere near that platform limit. The REST API overview also documents a default daily API allowance of 10,000 requests per app. [24]

For Phase 3.8.5, I would deliberately avoid Kintone's cursor API, even though it exists for large result sets, because creating a cursor uses POST. It does not mean the same thing as changing a record, but the current OrgFlow safety policy is stricter than necessary and benefits from having an unambiguous “GET only” rule. The current data volume does not require a cursor anyway. Kintone documents cursor creation separately and permits up to 500 records per cursor retrieval. [25]

Stable canonical tree hash

The connector renderer should prove that it did not mutate hierarchy:

async function computeCanonicalTreeHash(nodes) {  const canonical = nodes    .map((node) => ({      id: String(node.id),      parentId: node.parentId == null ? '' : String(node.parentId),    }))    .sort((a, b) => a.id.localeCompare(b.id))    .map(({ id, parentId }) => `${id}\u001F${parentId}`)    .join('\u001E');  const bytes = new TextEncoder().encode(canonical);  const hash = await crypto.subtle.digest('SHA-256', bytes);  return Array.from(new Uint8Array(hash))    .map((value) => value.toString(16).padStart(2, '0'))    .join('');}

Only hierarchy-defining canonical keys should participate in this particular hash. Employee display names, zoom, density and card dimensions should not.

Organization edges versus reporting edges

This is important enough to enforce at the type/model boundary:

function buildOrganizationEdges(canonicalNodes) {  const ids = new Set(canonicalNodes.map((node) => node.id));  return canonicalNodes    .filter((node) => node.parentId != null)    .map((node) => {      if (!ids.has(node.parentId)) {        throw new Error(          `Canonical orphan: ${node.id} -> missing ${node.parentId}`        );      }      return Object.freeze({        type: 'organization',        from: node.parentId,        to: node.id,      });    });}function buildVerifiedReportingEdges(reportingRows) {  return reportingRows    .filter((row) => row.verified === true)    .map((row) =>      Object.freeze({        type: 'reporting',        from: row.managerPositionId,        to: row.positionId,      })    );}

Never derive person/reporting edges from card position, title wording or ParentOrgCode.

In particular, do not hard-code “Managing Director → President” unless the verified reporting dataset explicitly says so.

DOM anchor measurement

W3C's CSSOM View specification defines getBoundingClientRect() as the geometry interface for an element's rendered bounding box. [26]

Because OrgFlow has one global transform, transformed viewport coordinates can be converted back to world coordinates:

function getUniformWorldScale(world) {  const visual = world.getBoundingClientRect();  if (world.offsetWidth <= 0 || world.offsetHeight <= 0) {    throw new Error('Org world has zero logical dimensions');  }  const scaleX = visual.width / world.offsetWidth;  const scaleY = visual.height / world.offsetHeight;  if (!Number.isFinite(scaleX) || !Number.isFinite(scaleY)) {    throw new Error('Invalid OrgFlow scale');  }  if (Math.abs(scaleX - scaleY) > 0.01) {    throw new Error(      `Non-uniform scaling detected: scaleX=${scaleX}, scaleY=${scaleY}`    );  }  return (scaleX + scaleY) / 2;}function measureNodeAnchors(element, world) {  const rect = element.getBoundingClientRect();  const worldRect = world.getBoundingClientRect();  const scale = getUniformWorldScale(world);  const toWorld = (viewportX, viewportY) => ({    x: (viewportX - worldRect.left) / scale,    y: (viewportY - worldRect.top) / scale,  });  return Object.freeze({    topCenter: toWorld(      rect.left + rect.width / 2,      rect.top    ),    bottomCenter: toWorld(      rect.left + rect.width / 2,      rect.bottom    ),    visualRect: rect,  });}

This should run only after the browser has settled the card layout:

That “two frame” policy is a practical OrgFlow synchronization rule rather than a platform requirement.

One scale transform

Do not transform individual departments, the connector SVG or specific branches:

function applyWorldTransform(world, {  scale,  translateX,  translateY,}) {  if (!(scale > 0)) {    throw new RangeError('Scale must be positive');  }  world.style.transformOrigin = '0 0';  world.style.transform =    `translate3d(${translateX}px, ${translateY}px, 0) scale(${scale})`;  world.dataset.orgflowScale = String(scale);}

Fit Readable versus Fit Entire Org

Cytoscape itself distinguishes fit/zoom operations and supports minimum zoom bounds, which reinforces the broader design principle that “fit” and “zoom” are viewport operations, not tree mutations. [28]

For OrgFlow, retain the stronger semantics developed during UAT:

Phase 3.8.5 implementation, Kintone safety, and migration

Minimal connector-layer implementation

Kintone's app.record.index.show can run whenever the list/custom view is displayed and again in response to view operations, so the runtime needs an idempotent initialization/disposal guard rather than blindly inserting a second SVG each time. [30]

I recommend this implementation sequence:

Freeze the current 3.8.4F baseline. Record the getBoundingClientRect() of the three top-level branches, major departments, representative position cards, world width/height and current scale. The connector patch must not materially change these dimensions.

Add an OrgFlow view guard. Initialize only on the Personnel View's verified viewId, not on every record list.

Fetch all data through a GET-only gateway. Use Kintone session-authenticated kintone.api() in the browser; request only required field codes. Kintone's Get Records endpoint supports session authentication and allows selecting fields, which also minimizes transferred/exposed data. [31]

Normalize an immutable snapshot. Construct organizationNodes, employees, positions, organizationEdges, and separately verifiedReportingEdges.

Calculate TREE_HASH_BEFORE. Reject initialization if canonical count, edge count, orphan count or expected root topology is invalid.

Reuse the existing cards unchanged. Insert only <svg class="orgflow-connectors"> behind them.

Wait for stable render and measure. Read node anchors in one batch using getBoundingClientRect().

Draw only visible structural edges. Hidden/collapsed descendant nodes do not get paths.

Install remeasurement triggers. ResizeObserver, density changes, expand/collapse, focus-subtree changes and any operation that changes card geometry call one debounced scheduleConnectorRender().

Validate before declaring readiness. Compare geometry to the 3.8.4F baseline, recalculate the canonical hash, inspect collisions/containment, check path anchors and perform a real screenshot UAT.

Zero-production-write enforcement

For Phase 3.8.5, production safety should be both architectural and testable.

The visualization bundle should contain no calls to record-add/update/delete endpoints. Kintone clearly separates Get Records (GET) from state-changing APIs such as status updates (PUT). [34]

Performance, accessibility, and UAT

Performance design

At the present project scale, 57 structural nodes and 275 employees do not justify a heavy virtualization framework by themselves. The performance checklist should be:

Keep collapsed staff collapsed. Do not instantiate 59 Die Casting employees merely to draw a “59 Staff” label.

Cache elementByNodeId; do not query the whole DOM for every edge.

Batch getBoundingClientRect() reads before SVG writes.

Reuse the existing SVG element and replace/update path children instead of rebuilding the application.

Recalculate connectors only after geometry-changing operations; pan and zoom should normally need no path recomputation if SVG and cards share the same transform.

Use ResizeObserver for actual container changes rather than polling. [33]

Keep Kintone reads out of viewport operations; Kintone documents API request limits, so visual interaction should stay entirely client-side after the snapshot loads. [24]

One particularly important result follows from the shared-world architecture:

Pan and zoom do not require recalculating connector coordinates at all.

If HTML cards and SVG paths live in the same coordinate space and their common ancestor is transformed, both move together. Connector recomputation is required only when layout geometry changes: density, expand/collapse, responsive re-packing, text-size change, or subtree focus reconstruction.

Accessibility design

WCAG 2.2 includes requirements around visible keyboard focus and minimum target sizes; the Target Size (Minimum) criterion specifies 24 by 24 CSS pixels unless an exception applies. WAI-ARIA's Authoring Practices also define keyboard interaction expectations for hierarchical/treegrid widgets. [36]

For OrgFlow:

Connectors are decorative semantics, so set SVG aria-hidden="true" and communicate hierarchy through card semantics, labels and keyboard behavior.

Every focused organization/position card needs a visible focus indicator.

Use a roving tabindex strategy rather than forcing users through every View Staff and Details button before reaching the next organizational node.

Enter/Space can open a node; Left/Right or Up/Down can navigate structural relations if OrgFlow explicitly implements the corresponding tree interaction model.

Do not assign role="tree" or treegrid" merely for appearance; use the ARIA pattern only if the required keyboard semantics are implemented. WAI-ARIA APG provides the expected keyboard model for treegrids. [37]

Focus Subtree should move programmatic focus to the new focused branch heading.

Search results should announce the matched person's name and organization through an appropriate live status region.

Do not encode Organization versus Reporting connectors by color alone.

Buttons such as Details, View Staff, Fit Readable and zoom controls should meet practical target sizing consistent with the WCAG minimum-target criterion. [38]

Prioritized recommendation

First choice — implement now:Native SVG connector overlay + existing OrgFlow DOM + selective D3 modules. D3 gives OrgFlow standards-based, low-level visualization and zoom primitives without forcing a new node layout, while SVG and actual DOM measurements satisfy the anchor and geometry requirements that the 3.8.4 iterations exposed. [41]

Fallback if the custom renderer eventually becomes too costly:Cytoscape.js + ELK. It provides an open-source graph model, zoom/pan/fit controls and mature layout extensions, but should be evaluated in a separate Kintone Custom View behind a feature flag rather than replacing the accepted OrgFlow view in-place. [3]

Commercial alternative:GoJS is the strongest candidate if licensing cost is acceptable and the objective changes from “preserve our accepted Kintone DOM” to “adopt a complete diagramming platform.” Its official org-chart sample, TreeLayout, link routing, Canvas/SVG rendering, zoom/scrolling and export support are a close functional match to the long-term OrgFlow requirements. [4]

Turnkey org-chart alternative:BALKAN OrgChart JS deserves a proof-of-concept if the organization prefers an org-chart-specific commercial product with built-in navigation and exports. Its existing licensing model and its ownership of layout make it less suitable for Phase 3.8.5 but potentially attractive for a future greenfield renderer. [16]

This solves the missing organization-chart semantics without reopening the geometry problems that phases 3.8.4C, 3.8.4D, 3.8.4E and 3.8.4F already solved.
