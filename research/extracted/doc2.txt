Professional Organization Charts in Kintone: JavaScript Rendering Architecture and Implementation Research

Executive summary

For a Kintone-based HR organization explorer with rich employee cards, variable-size departments, collapsed staff groups, search, zoom/pan, PDF/Excel export, and strict hierarchy integrity, the strongest architecture is not a monolithic charting library. The most controllable design is a hybrid:

Kintone records → canonical normalized model → runtime integrity validation → bottom-up layout engine → HTML/CSS node layer + SVG connector layer → one shared pan/zoom transform.

This architecture fits Kintone particularly well because Kintone exposes supported JavaScript event hooks and UI insertion points, while record data can be retrieved through its REST API. A full-screen chart can live in a Custom View, while toolbar controls can use supported Kintone UI spaces rather than modifying Kintone's internal DOM. Kintone's official examples use app.record.index.show for record-list customizations and kintone.app.getHeaderMenuSpaceElement() for controls. [1]

For your current OrgFlow implementation, I would not replace the Phase 3.8.4F layout with D3, GoJS, React Flow, or another renderer wholesale. You have already stabilized the difficult part: a variable-size 57-node organization structure with three visible top-level branches and collision-free packing. Replacing that renderer now would create unnecessary regression risk. The best next step is to preserve the existing HTML geometry and implement Phase 3.8.5 as an SVG connector layer, optionally using small D3 modules such as d3-selection and d3-zoom, rather than adopting full D3 rendering. D3 explicitly supports HTML, SVG and Canvas, its modules can be consumed independently, and its zoom behavior is rendering-technology agnostic. [2]

For a greenfield Kintone org chart, d3-org-chart is probably the fastest open-source route to a polished result: it is MIT-licensed, D3-based and designed specifically for organization charts, with custom content, expand/collapse, fit, centering, search, zoom and export capabilities. [3] For an enterprise product where commercial licensing is acceptable, GoJS offers much more built-in diagram infrastructure, including tree layout, link routing and image/SVG export; GoJS is commercial rather than open source. [4]

For complex DAG-like reporting structures rather than a strict organization tree, ELK Layered or a Sugiyama-family layout is stronger than ordinary tree layout. Sugiyama, Tagawa and Toda's 1981 framework was specifically developed for automatic visual representations of hierarchical system structures, while ELK today provides layered, tree, radial, force, rectangle-packing and other layout engines. [5]

The most important architectural rule is that organization structure and personnel reporting structure must remain two separate graph domains:

Organization structural edgeCanonical Parent Code    ↓Company → Division → Department → SectionPersonnel reporting edgeVerified Reports-To    ↓Position/Employee → Position/Employee

A department ParentCode must never be interpreted as an employee ReportsTo, and a visually senior title must never create a reporting edge automatically.

Kintone integration, data model, and integrity

A robust organization chart should treat Kintone as the system-of-record and application shell, not as the diagram layout engine. The viewer should read records, normalize them into a renderer-neutral graph, validate that graph, and only then render it.

Kintone's Get Records API returns at most 500 records per request, and the conventional offset method is limited to an offset of 10,000. Kintone documents seek, cursor and offset strategies for larger retrievals. [7] For your current scale of 57 organization nodes and 275 employees, record volume is modest, but implementing a GET-only seek reader still gives the chart a safe path to larger datasets without relying on the Cursor API.

Rendering pipeline

The important property of this pipeline is that screen layout is downstream from the canonical model. Compact/Normal/Comfortable modes, zoom, pan, staff expansion, branch packing and responsive reflow are not permitted to mutate parentCode, canonical identity or reporting relationships.

Canonical data model

For your use case, I recommend at least four explicit model types rather than one overloaded node structure.

For employee identity, use a canonical internal key such as an immutable HR identity or Kintone record identity. Keep employee number as a string, not a number. This matches the requirements already discovered in your OrgFlow data: a value such as 0043 must retain its leading zero, while duplicate business numbers such as 9000 cannot safely serve as a primary key.

A normalized representation can look like this:

function field(record, code, fallback = "") {  return record?.[code]?.value ?? fallback;}function normalizeOrganization(orgRecords) {  const nodes = orgRecords.map((r) => ({    id: String(field(r, "CanonicalCode")),    canonicalCode: String(field(r, "CanonicalCode")),    parentId: field(r, "ParentCode") || null,    parentCode: field(r, "ParentCode") || null,    name: String(field(r, "OrganizationName")),    entityType: String(field(r, "EntityType")),    level: Number(field(r, "HierarchyLevel", 0)),    hierarchyPath: String(field(r, "HierarchyPath")),    sortOrder: Number(field(r, "SortOrder", 0)),  }));  const orgEdges = nodes    .filter((n) => n.parentId)    .map((n) => ({      id: `org:${n.parentId}->${n.id}`,      source: n.parentId,      target: n.id,      type: "organization",    }));  return { nodes, orgEdges };}function normalizeEmployees(records) {  return records.map((r) => ({    // Prefer a dedicated immutable identity field when available.    employeeKey: String(field(r, "EmployeeUID", field(r, "$id"))),    employeeNumber: String(field(r, "EmployeeNumber")),    name: String(field(r, "EmployeeName")),    orgCode: String(field(r, "CanonicalOrgCode")),    positionId: String(field(r, "PositionId")),  }));}function normalizePositions(records) {  const positions = records.map((r) => ({    id: String(field(r, "PositionId")),    orgCode: String(field(r, "CanonicalOrgCode")),    title: String(field(r, "PositionTitle")),    occupantKey: String(field(r, "EmployeeUID")),    reportsToPositionId: String(field(r, "ReportsToPositionId")),  }));  // Only explicit/verified Reports-To values create reporting edges.  const reportingEdges = positions    .filter((p) => p.reportsToPositionId)    .map((p) => ({      id: `report:${p.reportsToPositionId}->${p.id}`,      source: p.reportsToPositionId,      target: p.id,      type: "reporting",    }));  return { positions, reportingEdges };}

Read-only Kintone retrieval

The following pattern uses GET requests only and follows the seek-pagination idea documented by Kintone. GET Records can return up to 500 records at a time. [10]

async function getAllRecordsReadOnly(appId, fields = []) {  const records = [];  let lastId = 0;  while (true) {    const params = {      app: appId,      query: `$id > ${lastId} order by $id asc limit 500`,    };    // Omitting "fields" makes $id reliably available for seek pagination.    if (fields.length > 0) {      params.fields = Array.from(new Set(["$id", ...fields]));    }    const response = await kintone.api(      kintone.api.url("/k/v1/records.json", true),      "GET",      params    );    if (!response.records.length) break;    records.push(...response.records);    const tail = response.records[response.records.length - 1];    lastId = Number(tail.$id.value);    if (response.records.length < 500) break;  }  return records;}

For a strict interpretation of your zero production writes rule, this is preferable to creating cursors, because the chart viewer can remain entirely GET-driven rather than invoking a POST merely to establish a read cursor.

Runtime topology validation and structural hashing

Hash only structural fields. UI state such as x, y, width, height, zoom, expansion, highlight, current search and viewport dimensions should not participate in the canonical tree hash.

Rendering architecture and layout algorithms

D3 itself deliberately works with web standards and can render through HTML, SVG or Canvas. Cytoscape.js, by contrast, primarily uses Canvas for rendering; vis-network also renders its network in HTML Canvas. [11] This difference matters significantly for an HR org chart because your nodes are not simple circles: they contain names, employee IDs, job titles, action buttons, staff counts, expansion controls, search highlighting and potentially accessible interactive content.

My architecture recommendation is therefore an inference from those rendering models: rich employee/organization cards are easiest to maintain as normal HTML, while links are easiest to render as SVG paths behind those cards.

Layout algorithm choice

D3's tree layout implements the Reingold–Tilford tidy-tree approach and notes the linear-time improvement by Buchheim and collaborators. The original Reingold–Tilford work targeted aesthetically compact tree drawings; Buchheim, Jünger and Leipert later published a linear-time improvement to Walker's general-tree algorithm. [12]

Sugiyama's layered framework addresses more general hierarchical directed structures; this becomes useful when reporting relationships form a DAG rather than a pure tree. [13] ELK provides production-oriented layered, tree, force, radial and rectangle-packing algorithms, among others. [14]

D3 supports both Cartesian and polar hierarchical forms and provides a separate force-layout module, while ELK exposes radial, force and layered alternatives. [15]

Why bottom-up intrinsic sizing fits your chart

The hard problem in your organization is not the number of nodes. It is that one department may contain one short section while another contains many management cards, collapsed employee groups and deeper subunits.

A percentage allocation such as:

DIV-ME = 44%DIV-G0 = 36%Corporate = 20%

is fundamentally less robust than:

Measure leaf cards      ↓Measure sections      ↓Pack section siblings      ↓Measure departments      ↓Pack department siblings      ↓Measure divisions      ↓Pack top-level divisions      ↓Natural tree width/height      ↓One global transform

The second design guarantees that a parent's size is derived from the content it must contain. It also explains why your later Phase 3.8.4E/F layouts became much more stable after moving away from percentage squeezing.

Connector strategy

For a classic organization chart, use orthogonal connectors rather than diagonal paths:

             Parent               │               │        ───────┼────────        │      │       │      Child  Child   Child

For parent P and child C, define:

P = parent bottom-center anchorC = child top-center anchorM = Y coordinate in the gap between parent and child rowM P.x P.yV MH C.xV C.y

This produces the SVG path:

`M ${px} ${py} V ${midY} H ${cx} V ${cy}`

A more polished implementation groups children under a common parent into one horizontal sibling bus, so the shared segment is rendered once.

For your application, connector semantics should remain explicitly separated:

const connectorSets = {  organization: orgEdges,        // canonical Parent Code  reporting: reportingEdges,     // explicit verified Reports-To};

This prevents a visual layout engine from inventing personnel reporting relationships.

Responsive model

D3's zoom behavior supports mouse/touch zoom and pan and can restrict both scale and translation; it is agnostic to HTML, SVG or Canvas. [16] That makes it useful even when D3 does not own the node renderer.

The correct responsive model is:

ResizeObserver      ↓Measure available viewport      ↓Repack variable-size sibling groups      ↓Recalculate natural dimensions      ↓Preserve user zoom/focus      ↓Redraw connectors

not:

Resize  ↓Scale entire chart smaller until everything fits

Your distinction between Fit Readable and Fit Entire Org is therefore architecturally sound:

Fit Readable    scale ∈ [0.70, 1.00]    height may overflow    pan/scroll allowedFit Entire Org    scale may fall below 0.70    overview only

This is particularly important for desktop HR systems because fitting the full tree mathematically is not the same as making it usable.

D3.js

D3 is the strongest low-level choice for this project because it does not force you to surrender ownership of the DOM. D3 is intentionally low-level, web-standard based and capable of working with HTML, SVG and Canvas. Its hierarchy module turns tabular parent IDs into hierarchy structures through stratify, and d3-zoom can handle the world transform independently of the renderer. [25]

Pros for Kintone: framework-free, works directly inside Kintone customization, modular, ideal for a custom SVG connector overlay, easy to coexist with your existing cards.

Cons: D3 gives building blocks rather than a finished HR organization chart. Collision logic, variable-size subtree packing, export semantics and card interaction remain your responsibility.

d3-org-chart

The open-source bumbeishvili/org-chart project is specifically designed for org charts and is MIT licensed. Its documented feature set includes custom node content, expand/collapse, fit, centering/highlighting, zoom, export, search, multiple roots, horizontal views, paging and data-driven size. [3]

For a new project this would be my quick-integration winner. For your existing chart, however, replacing the approved layout would be unnecessary. One additional enterprise consideration is to review transitive dependency licenses during your legal/software-composition scan rather than assuming the top-level MIT license is the only license involved.

Example shape:

dagre-d3

Dagre-D3 is an MIT-licensed D3 renderer for directed graph layouts and is natural for layered graph structures. [19] It is a stronger fit for flat graph nodes plus edges than for the highly nested visual containers you now have in DIV-ME/DIV-G0.

async function renderWithDagreD3(model, svgElement) {  const graph = new dagreD3.graphlib.Graph()    .setGraph({ rankdir: "TB", nodesep: 28, ranksep: 60 })    .setDefaultEdgeLabel(() => ({}));  for (const node of model.nodes) {    graph.setNode(node.id, {      label: node.name,      width: 220,      height: 90,    });  }  for (const edge of model.orgEdges) {    graph.setEdge(edge.source, edge.target);  }  const inner = d3.select(svgElement).append("g");  new dagreD3.render()(inner, graph);  return {    type: "svg",    connectorMode: "native",    instance: graph,  };}

Cytoscape.js

Cytoscape.js is MIT-licensed, dependency-free at its core, Canvas-rendered, and supports PNG/JPG/SVG output; its extension ecosystem includes ELK integration. [26] This is excellent for relationship/network views, but it is less natural when every employee node should remain a conventional HTML card with buttons, tooltips and complex responsive content.

async function renderWithCytoscape(model, mount) {  const elements = [    ...model.nodes.map((n) => ({      data: { id: n.id, label: n.name },    })),    ...model.orgEdges.map((e) => ({      data: {        id: e.id,        source: e.source,        target: e.target,      },    })),  ];  const cy = cytoscape({    container: mount,    elements,    layout: {      name: "breadthfirst",      directed: true,      spacingFactor: 1.2,    },  });  return {    type: "canvas",    connectorMode: "native",    instance: cy,  };}

For Canvas renderers, getBoundingClientRect() measures the chart canvas, not individual Cytoscape nodes. Node collision validation therefore needs Cytoscape's internal node bounding boxes rather than DOM rectangles. That is one reason the HTML/SVG architecture is simpler for your existing UAT metric strategy.

GoJS

GoJS is a commercial diagramming framework rather than an open-source library; deployed applications require an appropriate license key. [27] Its TreeLayout provides spacing, compaction, breadth limits, child-row wrapping, sorting and link routing controls. [28] That makes it much closer to a complete diagram platform than D3.

GoJS also documents SVG and raster export APIs, including Diagram.makeSvg() and image creation. [29]

OrgChart.js / dabeng OrgChart

Dabeng's OrgChart is MIT licensed and supports JSON data, expand/collapse, four orientations, pan/zoom, node customization and multiple/hybrid approaches for larger organization charts. [32] Its export example uses client-side browser helpers including html2canvas and jsPDF. [33]

async function renderWithDabeng(model) {  const nested = toNestedTree(model.nodes);  const chart = new OrgChart({    chartContainer: "#orgflow-chart",    data: nested,    pan: true,    zoom: true,    nodeId: "id",    nodeTitle: "name",  });  return {    type: "dom",    connectorMode: "native",    instance: chart,  };}

It is attractive for a simple conventional org chart. Your current complex layout, however, already exceeds the typical “one card per hierarchy node” pattern.

React Flow

React Flow is MIT licensed and designed for node-based interfaces in React. [34] Its edges are SVG-based, and its official API provides straight, Bézier, simple-Bézier and smooth-step path generation plus fully custom SVG edges. [35]

function OrgFlowGraph({ model }) {  const nodes = model.nodes.map((n) => ({    id: n.id,    position: layoutPositions.get(n.id),    data: n,    type: "orgCard",  }));  const edges = model.orgEdges.map((e) => ({    id: e.id,    source: e.source,    target: e.target,    type: "smoothstep",  }));  return (    <ReactFlow      nodes={nodes}      edges={edges}      nodeTypes={nodeTypes}      fitView={false}    />  );}

It is a good choice if OrgFlow becomes a React application or an interactive node editor. For vanilla Kintone, React itself becomes an additional architectural dependency without solving a problem your current renderer cannot already solve.

vis-network

Vis Network uses Canvas, supports hierarchical layout and offers settings such as level separation, node spacing, tree spacing and directed ordering. [24] It is dual-licensed under MIT and Apache 2.0. [36]

Vis-network's own repository positions it as a general network visualization capable of handling up to a few thousand nodes/edges with clustering for larger cases. [36] That scale is unnecessary for the current 57-node corporate tree, while Canvas gives up much of the HTML-card advantage.

Bottom-up intrinsic subtree measurement pseudocode

measureSubtree(node):    measure node's own header / visible cards    if no structural children:        requiredWidth  = ownMinimumWidth        requiredHeight = ownContentHeight        return metrics    childMetrics =        for each structural child:            measureSubtree(child)    candidateArrangements =        pack children with 1 column        pack children with 2 columns        ...        pack children with max allowed columns    reject candidate if:        any child becomes narrower than minimum readable width        any child overlaps another child    score candidate using:        total height        unused horizontal area        row imbalance        number of isolated items in last row        readability penalty    best = candidate with lowest cost    node.requiredWidth =        max(            ownMinimumWidth,            best.requiredWidth + horizontalPadding * 2        )    node.requiredHeight =        ownHeaderHeight        + verticalGap        + best.requiredHeight        + verticalPadding * 2    store child x/y offsets from best arrangement    return node metrics

A vanilla-JavaScript version:

const LAYOUT = Object.freeze({  gapX: 16,  gapY: 16,  paddingX: 16,  paddingY: 16,  maxColumns: 4,});function chunk(array, size) {  const result = [];  for (let i = 0; i < array.length; i += size) {    result.push(array.slice(i, i + size));  }  return result;}function evaluatePacking(children, columns) {  const rows = chunk(children, columns);  let totalHeight = 0;  let maxRowWidth = 0;  let unusedSlots = 0;  const positioned = [];  rows.forEach((row, rowIndex) => {    const rowWidth =      row.reduce((sum, child) => sum + child.width, 0) +      Math.max(0, row.length - 1) * LAYOUT.gapX;    const rowHeight = Math.max(      ...row.map((child) => child.height)    );    maxRowWidth = Math.max(maxRowWidth, rowWidth);    if (rowIndex > 0) {      totalHeight += LAYOUT.gapY;    }    let x = 0;    for (const child of row) {      positioned.push({        child,        x,        y: totalHeight,      });      x += child.width + LAYOUT.gapX;    }    totalHeight += rowHeight;    unusedSlots += columns - row.length;  });  // Penalize tall layouts and awkward sparse final rows.  const score =    totalHeight +    maxRowWidth * 0.08 +    unusedSlots * 40;  return {    columns,    width: maxRowWidth,    height: totalHeight,    positioned,    score,  };}function measureSubtree(node) {  const childLayouts =    node.children.map(measureSubtree);  const candidates = [];  for (let columns = 1; columns <= maxColumns; columns++) {    candidates.push(      evaluatePacking(childLayouts, columns)    );  }  candidates.sort((a, b) => a.score - b.score);  const best = candidates[0];  const width = Math.max(    node.intrinsicWidth,    best.width + LAYOUT.paddingX * 2  );  const height =    node.intrinsicHeight +    LAYOUT.gapY +    best.height +    LAYOUT.paddingY * 2; This is intentionally not a general Sugiyama implementation. It is a layout policy optimized for your variable-size corporate subtree containers.

For a strict single-node-per-tree-node model, D3's built-in tree layout already provides compact Reingold–Tilford positioning. [37] For compound DAGs or advanced routing, ELK Layered is a better alternative to continuously extending a home-grown algorithm. ELK's current reference includes many options covering spacing, edge routing, crossing minimization, hierarchy handling and related constraints. [38]

Fit Readable algorithm

The most important constraint is that Fit Readable should never use chart height to force a scale below readability. Height may overflow and the viewport can scroll vertically.

const MIN_READABLE_SCALE = 0.70;const MAX_READABLE_SCALE = 1.00;const TARGET_WIDTH_USAGE = 0.90;function clamp(value, min, max) {  return Math.max(min, Math.min(max, value));}async function fitReadable() {  const viewport =    document.querySelector("#orgflow-viewport");  const world =    document.querySelector("#orgflow-world");  // worldNaturalWidth should be produced by the layout engine  // and explicitly assigned so offsetWidth represents the model.  const naturalWidth = world.offsetWidth;  if (!naturalWidth) {    throw new Error("Cannot Fit Readable: natural width is 0");  }  const targetWidth =    viewport.clientWidth * TARGET_WIDTH_USAGE;  const calculatedScale =    targetWidth / naturalWidth;  const scale = clamp(    calculatedScale,    MIN_READABLE_SCALE,    MAX_READABLE_SCALE  );  viewState.scale = scale;  // Horizontal center. Negative pan is fine when tree is  // wider than the viewport.  viewState.panX =    (viewport.clientWidth - naturalWidth * scale) / 2;  // Keep company leadership near the top rather than vertically  // centering an extremely tall tree.  viewState.panY = 24;  applyWorldTransform();  await afterTwoFrames();  const actualWidth =    world.getBoundingClientRect().width;  const actualScaleRatio =    actualWidth / naturalWidth;  const scaleError =    Math.abs(actualScaleRatio - scale);  if (scaleError > 0.02) {    throw new Error(      `Scale validation failed: commanded=${scale}, ` +      `actual=${actualScaleRatio}`    );  }  return {    naturalWidth,    viewportWidth: viewport.clientWidth,    commandedScale: scale,    actualScaleRatio,    actualWidth,    widthUsagePercent:      (actualWidth / viewport.clientWidth) * 100,  };}

Collision detection

Do not compare every nested container against every other nested element, because a child should naturally intersect its parent. Collision detection should compare visual peers such as siblings, top-level branches or cards within a packing group.

function rectanglesOverlap(a, b, gap = 0) {  return !(    a.right + gap <= b.left ||    b.right + gap <= a.left ||    a.bottom + gap <= b.top ||    b.bottom + gap <= a.top  );}function detectSiblingCollisions(parentId, gap = 4) {  const elements = [    ...document.querySelectorAll(      `[data-layout-parent="${CSS.escape(parentId)}"]`    ),  ].filter(    (el) =>      !el.hidden &&      el.getClientRects().length > 0  );  const collisions = [];  for (let i = 0; i < elements.length; i++) {    for (let j = i + 1; j < elements.length; j++) {      const a = elements[i];      const b = elements[j];      const rectA = a.getBoundingClientRect();      const rectB = b.getBoundingClientRect();      if (rectanglesOverlap(rectA, rectB, gap)) {        collisions.push({          a:            a.dataset.orgNodeId ??            a.dataset.positionId ??            a.id,          b:            b.dataset.orgNodeId ??            b.dataset.positionId ??            b.id,          rectA,          rectB,        });      }    }  }  return collisions;}function detectAllSiblingCollisions() {  const parentIds = new Set(    [...document.querySelectorAll("[data-layout-parent]")]      .map((el) => el.dataset.layoutParent)      .filter(Boolean)  );  return [...parentIds].flatMap((parentId) =>    detectSiblingCollisions(parentId)  );}

For the present chart size, an O(n²) peer collision check is perfectly reasonable. If the chart eventually grows by orders of magnitude, a spatial index can replace pairwise comparison.

Performance, accessibility, export, caching, and production safety

At 57 organization nodes and 275 employees, the system does not need a Canvas renderer for performance. The larger performance risk is unnecessary full DOM reconstruction when staff groups, density or viewport dimensions change.

A good interaction budget is:

Pan / Zoom    → transform only    → NO relayout    → NO data fetch    → NO structural hash regeneration requiredResize    → debounce    → repack if geometry threshold changed    → redraw connectorsExpand / Collapse subtree    → recalculate affected subtree    → propagate parent dimensions upward    → reposition affected siblings    → redraw connectorsSearch    → index lookup    → highlight    → pan/center target    → NO hierarchy mutation

D3 zoom is specifically designed to handle multiple input modalities and can constrain scale/translation, so it is a good interaction layer even when the node/layout implementation is custom. [16]

ResizeObserver callbacks should schedule layout through requestAnimationFrame or a 75–150 ms debounce rather than re-running the entire geometry engine on every intermediate resize event. For React Flow, the project's own performance guidance emphasizes minimizing unnecessary node/edge state changes and memoizing expensive components; the same principle applies to vanilla Kintone. [39]

Virtualization is probably unnecessary for the canonical 57 organization nodes. It becomes useful if hundreds or thousands of employee cards are simultaneously expanded. A better first optimization is aggregation:

Die Casting59 Staff[ View Staff (59) ]

rather than rendering all 59 employee cards on initial load.

Accessibility

The HTML+SVG architecture has an important practical advantage: card content can remain ordinary semantic HTML. This is an architectural inference based on the fact that D3 can operate on normal HTML/SVG, whereas Cytoscape.js and vis-network render their graph content on Canvas. [11]

Recommended semantics include:

<article  class="org-card"  data-org-node-id="TMT0"  aria-labelledby="org-TMT0-name">  <h3 id="org-TMT0-name">    Machinery Department  </h3>  <button    aria-expanded="false"    aria-controls="staff-TMT0"  >    View Staff (15)  </button>  <div id="staff-TMT0" hidden>    ...  </div></article>

Keyboard users should be able to operate search, staff expansion, focus-subtree and toolbar controls without relying on drag-to-pan. Zoom buttons should supplement, not replace, pointer-wheel zoom. Focus should remain visible after search or subtree focusing.

Connector SVG should generally use:

<svg aria-hidden="true" ...>

because the visual line is redundant when the underlying semantic parent/child relationship is represented in accessible content and navigation.

PDF and Excel consistency

The key export rule should be:

Web, Excel and PDF consume one normalized canonical model; they do not consume one another.

Kintone's official Excel-export tutorial demonstrates client-side Excel generation from records using SheetJS and FileSaver. [40] That is the correct conceptual approach: Excel should serialize canonical data rows, not scrape the current visible DOM.

Quick-integration option

For a new Kintone application where the desired result is a conventional employee org chart rather than your current compound Division→Department→Section→Position layout:

Use d3-org-chart.

It already targets organization charts and supports many of the interactions you have been implementing manually. [3]

Recommended stack:

Kintone Custom View+d3-org-chart+Kintone REST GET+canonical adapter+Web Crypto hash validator+SheetJS Excel+dedicated PDF exporter

Estimated production effort: approximately 1–2 weeks for a modest chart, more if the canonical hierarchy contains mixed organization nodes and personnel-reporting nodes.

Primary risk: the more you need branch-specific layouts like “four departments across, but management positions internally in a three-column grid,” the more you begin fighting a generic org-chart library's layout assumptions.

Balanced option — my recommendation

Use:

Kintone+Vanilla JS / TypeScript+HTML/CSS cards+SVG connector layer+custom bottom-up intrinsic layout+D3 hierarchy/zoom only where useful

This keeps the DOM fully accessible and measurable, supports your getBoundingClientRect() UAT process, separates structural and reporting connectors cleanly, and preserves the layout engine already proven in your Human UAT.

Estimated effort from the current state: the difficult geometry work is already largely complete; a hardened connector layer plus validation is materially less work than replacing the entire chart.

Primary risk: custom geometry must remain covered by automated collision and scale tests, because there is no library vendor guaranteeing the layout.

Enterprise-grade option

There are two credible enterprise routes.

GoJS is the first when commercial licensing is acceptable. It gives a full diagram platform with tree layout, configurable spacing/compaction, link routing and export facilities, at the cost of a commercial license and a significant migration from your current DOM renderer. [4]

The open-source-oriented alternative is:

HTML/CSS presentation+SVG connectors+ELK.js layout computation

ELK is specifically a layout kernel rather than a viewer; the Eclipse project describes it as a collection of layout algorithms plus infrastructure bridging layout algorithms and diagram viewers/editors. [47] Its available algorithms include Layered, tree-oriented approaches, radial, force and rectangle packing. [48] ELK's Layered algorithm is particularly attractive if future OrgFlow requirements introduce multiple reporting lines, matrix management, dotted-line relationships or other structures that cease to be a pure tree.

ELK 0.12.0 is present in the current Eclipse release line as of 2026, so unlike legacy mxGraph it is an actively current layout technology. [49]
